# AGENTS.md — универсальные правила работы

Этот файл содержит постоянные правила для Codex и подходит для разных репозиториев. Конкретные требования проекта брать из его документации, кода, тестов и текущего задания пользователя.

## Продолжение работы между чатами

- В начале каждой задачи прочитать `PROJECT_STATUS.md`, если он существует.
- Если проект рассчитан более чем на одну задачу, а `PROJECT_STATUS.md` отсутствует, создать его.
- Перед завершением каждой выполненной задачи обновить `PROJECT_STATUS.md`.
- Записывать только:
  - что уже реализовано;
  - текущее состояние проекта;
  - важные принятые решения;
  - известные проблемы;
  - что рекомендуется делать следующим;
  - какие проверки прошли;
  - последний связанный commit.
- Не превращать `PROJECT_STATUS.md` в подробную историю переписки или список всех мелких изменений.
- Удалять или исправлять устаревшую информацию.
- Изменение `PROJECT_STATUS.md` включать в тот же commit и push, что и выполненную задачу.

## 1. Область задачи

- Одна задача или один чат — один ограниченный, законченный и проверяемый смысловой блок.
- Не проводить полную ревизию всего репозитория, если пользователь явно этого не запросил.
- Для локальной задачи изучать только относящиеся к ней документы, код, тесты и непосредственные зависимости.
- Не расширять неопределённые формулировки вроде «и так далее» до самостоятельной переделки проекта.
- Не реализовывать весь roadmap одним проходом.
- Сначала найти существующую реализацию. Не создавать параллельный компонент, сервис или систему рядом с уже работающими.
- Делать минимально достаточное изменение без попутного массового рефакторинга и форматирования.

## 2. Приоритет инструкций

При противоречиях соблюдать следующий порядок:

1. Текущая явная команда пользователя.
2. Более близкий к изменяемому файлу `AGENTS.md`, если он существует.
3. Корневой `AGENTS.md`.
4. Главные документы проекта: specification, README, architecture, roadmap и инструкции соответствующего модуля.
5. Существующий код и тесты — фактическое поведение, которое нельзя ломать случайно.

Не считать старый checklist, комментарий, mockup или название коммита доказательством текущего состояния. При необходимости сверять информацию с кодом, тестами и релевантной историей Git.

## 3. Начало работы

Перед изменениями:

1. Выполнить `git status --short --branch`.
2. Определить структуру проекта, используемый стек и команды из README, package-файлов и CI.
3. Прочитать только релевантные инструкции и существующую реализацию.
4. Проверить историю затрагиваемых файлов, если причина текущего решения неочевидна.
5. Для сложной задачи сформулировать короткий план; простую правку выполнять сразу.

Если рабочее дерево уже изменено, считать эти изменения принадлежащими пользователю. Не стирать, не перезаписывать и не включать их в свой commit. Если изменения пересекаются с задачей, остановиться и объяснить конфликт.

## 4. Изменение кода

- Соблюдать существующую архитектуру, стиль, соглашения и границы модулей.
- Изменять только файлы, необходимые для задачи.
- Не удалять работающую функцию без явной необходимости или команды пользователя.
- Не дублировать уже существующую бизнес-логику.
- Не создавать чрезмерно большие классы, компоненты и файлы, смешивающие независимые обязанности.
- Сложные или долгие операции не выполнять синхронно, если проект уже использует очереди или фоновые задачи.
- Внешние сервисы подключать через существующие abstractions/interfaces и с полноценной обработкой ошибок.
- Не создавать fake/mock integration и не выдавать её за готовую функцию.
- Пользовательские строки выносить в принятую проектом систему локализации; не принимать данные или пользовательский контент за UI-строки.
- Изменения схемы данных делать совместимыми с существующими данными. Не применять destructive migrations без прямого разрешения.
- При изменении наблюдаемого поведения или исправлении ошибки добавить либо обновить тест.

## 5. Безопасность и данные

- Никогда не добавлять в Git `.env`, пароли, tokens, API keys, cookies, private keys, дампы БД, production logs и приватные пользовательские данные.
- Не просить пользователя присылать секреты в чат и не менять credentials, remote URLs или глобальный Git config.
- Не ослаблять authentication, authorization, validation, rate limits или security headers без явной причины и тестов.
- Не обходить ограничения внешних сервисов, permissions или server policy.
- Массовое удаление, перемещение или необратимое преобразование данных требует явного подтверждения и плана восстановления.

## 6. Проверки

- Определять команды проверки из документации, package-файлов и CI самого проекта; не придумывать произвольную замену.
- Запускать минимальный достаточный набор тестов, линтеров, type checks и build для изменённой области.
- Полный набор проверок запускать для широких, архитектурных и cross-cutting изменений.
- Перед завершением проверить `git diff --check`, `git diff --stat` и содержательный diff.
- Если проверка уже прошла на текущем неизменённом рабочем дереве, не запускать её повторно только ради commit или push.
- Если после проверки код изменился, повторить затронутые проверки.
- Не утверждать, что тест или build прошёл, если он не запускался. Точно указывать недоступные проверки и причину.

Документационная правка обычно не требует полного набора программных тестов, если она не меняет executable examples, configuration или generated documentation.

## 7. Git: commit и push

- Один законченный смысловой блок — один atomic commit.
- Не делать commit после каждой промежуточной мелочи и не объединять независимые задачи в один commit.
- После завершённой задачи и успешных релевантных проверок выполнить commit и push текущей ветки, если пользователь явно не запретил Git-операции.
- Перед commit проверить status и diff; добавлять только файлы текущей задачи.
- Использовать короткое содержательное commit message в imperative style, описывающее результат.
- Не выполнять повторную ревизию проекта и не перезапускать уже пройденные проверки только для составления commit message или push.
- Не использовать `push --force`, `reset --hard`, destructive checkout, amend или rebase опубликованной истории без прямого указания пользователя.
- Не использовать stash для сокрытия пользовательских изменений без прямой команды.
- Не создавать новую ветку, pull request или tag без запроса. Работать в текущей ветке и отправлять изменения только в её настроенный upstream.
- Если remote содержит новые коммиты или push отклонён, не применять force-push. Сообщить о расхождении и интегрировать изменения безопасно только в рамках разрешённой задачи.
- При получении обновлений предпочитать fast-forward (`git pull --ff-only`), если проект не устанавливает другой workflow.

Commit и push не являются deployment. Не публиковать приложение, не выполнять серверные команды и не изменять production без явной команды пользователя или установленного проектом процесса.

## 8. Документация и статус

- Обновлять документацию, если изменение действительно меняет архитектуру, установку, команды, API, workflow или подтверждённый статус.
- Не переписывать большое ТЗ ради небольшой функции.
- Не отмечать пункт выполненным, пока реализация и необходимые проверки не завершены.
- Планируемую или частично реализованную функцию не описывать как готовую.

## 9. Итоговый ответ

После выполнения кратко сообщить:

- что изменено;
- какие проверки реально запущены и прошли;
- commit hash и сообщение, если commit создан;
- ветку и remote, куда выполнен push, если он выполнен;
- что осталось незавершённым или требует решения пользователя.

Не повторять в отчёте всё техническое задание и не скрывать ограничения результата.
