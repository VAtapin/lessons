# Техническое задание на платформу lessons.atapin.de

Редакция 1.0 от 30 сентября 2026 года. Полный документ для рассмотрения владельцем проекта перед реализацией.

Документ объединяет согласованные требования и план создания движка, конструктора, библиотеки блоков, медиатеки и инструментов проведения занятий. Требования описывают будущую систему: наличие этого документа не означает, что функции уже реализованы. Предложения, которые требуют отдельного решения, явно перечислены в разделе 25.

Для первого чтения: разделы 1–4 описывают продукт, раздел 24 — порядок разработки, раздел 25 — оставшиеся решения, раздел 26 — условия готовности. Подробные требования к отдельным возможностям находятся в разделах 5–23.

Рекомендуемые модели и режимы рассуждения для отдельных работ, с ограничением использования Astra, описаны в [плане выбора моделей](IMPLEMENTATION_MODEL_PLAN.md). Этот план не изменяет требования к качеству и приёмке.

## 1. Назначение и основной результат

1.1. Создать платформу для подготовки и проведения интерактивных христианских занятий на домене `lessons.atapin.de`.

1.2. Основной продукт — расширяемый движок и инструменты учителя. Учитель собирает материалы из повторно используемых блоков; разработчик добавляет новые механики через единый интерфейс расширений.

1.3. Одна библиотека блоков и изображений используется во множестве уроков. Количество уроков не должно требовать создания отдельных приложений, пультов или серверных API для каждой темы.

1.4. Полная первая платформенная версия включает конструктор, библиотеку, медиатеку, проведение занятий, кабинет и историю, совместное проведение, мультиязычность и публичный каталог с гостевым запуском.

1.5. Разработка идёт по небольшим проверяемым этапам. Первый технический прототип существенно меньше полной платформенной версии и не объявляется готовой платформой.

## 2. Границы работ и исходные материалы

2.1. Сначала создаются инструменты и блоки. Создание и перевод конкретных учебных уроков — последующее самостоятельное наполнение.

2.2. `OLD/kto-moi-blizhnii` используется как источник возможных идей, материалов и примеров взаимодействия. Перенос всех 13 этапов, сохранение прежней структуры, баллов и полного поведения не является обязательным этапом или критерием приёмки.

2.3. Для проверки применяются короткие технические сборки блоков, включая несколько разных сочетаний. Они не выдаются за подготовленные педагогические материалы публичного каталога.

2.4. Визуальные источники:

- [Макет главной страницы](../UI-Design/UI-Design.png).
- [Утверждённый макет пульта](../UI-Design/teacher-panel-concept-v1.png).
- [Уточнения UI пульта](../UI-Design/teacher-panel-ui.md).

2.5. Макет пульта утверждён с двумя обязательными дополнениями: полностью скрываемое главное меню и отделяемая панель управления. Демонстрационные имена, числа и задания на изображении не являются фиксированными данными продукта.

2.6. В первую версию не входят: постоянные ученические аккаунты, полноценная автономная работа без интернета, одновременное редактирование одного черновика несколькими авторами, произвольная загрузка программного кода учителями, магазин расширений, генерация уроков ИИ и полный набор экспортов PDF/PPTX. Их возможное добавление не должно задерживать согласованный объём.

## 3. Пользователи и права

3.1. Права проверяются на сервере. Скрытая кнопка или неизвестный пользователю адрес не являются механизмом ограничения доступа.

| Роль или возможность | Разрешённые действия |
| --- | --- |
| Посетитель | Просматривать опубликованные материалы и выбирать урок |
| Гостевой учитель | Запустить доступный урок, владеть созданным занятием, управлять им в пределах срока гостевого доступа |
| Учитель с аккаунтом | Сохранять личные материалы и медиа, пользоваться конструктором, историей и гостевыми возможностями |
| Владелец занятия | Управлять доступом помощников, завершать занятие, назначать ведущего и возвращать управление |
| Активный ведущий | Переключать этапы, запускать задания и общие действия, управлять таймером |
| Помощник | Видеть разрешённые учителю данные, работать с участниками и модерировать ответы |
| Ученик | Войти в занятие, получать предназначенный ему материал, выполнять разрешённые задания |
| Экран проектора | Получать только данные общего показа без учительских заметок и прав управления |
| Администратор | Управлять публичным каталогом, справочниками, общей библиотекой и публикациями |

3.2. Владение занятием и роль активного ведущего независимы. Владелец может передать ведение и при этом сохранить право вернуть управление.

3.3. Учитель может одновременно пользоваться несколькими своими вкладками. Это один участник управления, а не несколько независимых ведущих.

3.4. Доступ к проведению занятия не даёт права редактировать исходный урок или просматривать другие личные материалы его автора.

## 4. Основные пользовательские сценарии

4.1. Гостевой запуск: открыть каталог → выбрать опубликованный материал и язык → просмотреть условия → начать занятие → показать код/QR → провести → завершить.

4.2. Создание: открыть конструктор → создать этапы → добавить блоки и изображения → проверить → сохранить версию → провести.

4.3. Повторное использование: сохранить настроенный блок в библиотеку → вставить его в другой материал → изменить локальный экземпляр, сохранив исходную заготовку.

4.4. Возвращение: открыть кабинет → выбрать незавершённое занятие → продолжить с сохранённого состояния. Повторное проведение завершённого материала создаёт новое занятие.

4.5. Помощник: владелец выдаёт приглашение → коллега получает отдельный доступ → помогает с ответами → при необходимости принимает ведение.

4.6. Маленький экран: свернуть главное меню → вынести пульт в отдельную вкладку или компактное окно → продолжить управление тем же занятием.

4.7. Программное расширение: разработчик добавляет новый тип блока → регистрирует его через контракт → компонент доступен редактору и движку без создания отдельной системы уроков.

4.8. Режим без телефонов: учитель использует общий экран, ведёт обсуждение и открывает результаты. Индивидуальные ответы не имитируются; упражнения, требующие устройств, обозначаются заранее.

## 5. Структура данных и версии

5.1. Основная структура содержания: **Lesson → Lesson Version → Stage → Block Instance**.

| Сущность | Назначение |
| --- | --- |
| Lesson | Идентичность материала, владелец, принадлежность и каталог версий |
| Lesson Version | Содержание, переводы и ссылки на медиа конкретной редакции |
| Stage | Упорядоченный этап: название, расположение блоков, рекомендуемое время, заметки ведущему |
| Block Type | Программная механика, формат настроек и допустимое поведение |
| Block Template | Сохранённая заготовка блока с содержанием и настройками |
| Block Instance | Конкретное использование блока внутри версии урока |
| Media Asset | Идентичность медиафайла, владелец, метки и сведения об источнике |
| Media Version | Неизменяемый файл определённой версии и его технические характеристики |
| Session | Конкретное проведение фиксированной версии материала |
| Session Participant | Участник конкретного занятия, его роль и статус подключения |
| Block Runtime State | Состояние конкретного экземпляра блока в конкретном занятии |
| Response | Ответ участника с привязкой к занятию, экземпляру и попытке |
| Invitation | Ограниченное приглашение к проведению занятия |

5.2. Опубликованная версия неизменяема с момента публикации. Правка создаёт новый черновик, а не переписывает старую версию.

5.3. Выпуск версии для личного проведения и размещение в общем каталоге — разные операции. Частный материал можно проводить без публикации для всех посетителей.

5.4. Репетиция черновика фиксирует временный снимок содержания. Дальнейшие изменения редактора не меняют уже запущенную репетицию; её результаты не смешиваются с историей реальных занятий.

5.5. Ответы, участники, таймеры и выполненные задания никогда не записываются в общую заготовку или содержание урока.

5.6. Даже два использования одной заготовки в одном уроке получают разные идентификаторы экземпляров. Состояние хранится с привязкой как минимум к занятию и экземпляру; личные ответы дополнительно привязаны к участнику.

5.7. Архивирование материала скрывает его из выбора для новых запусков, сохраняя ссылки, необходимые существующим занятиям. Удаление персональных данных выполняется по отдельным правилам раздела 17; неизменяемость содержания не оправдывает бессрочное хранение ответов детей.

## 6. Повторное использование блоков

6.1. При вставке заготовки создаётся самостоятельный экземпляр с копией её содержания и настроек и ссылкой на происхождение. Медиа при этом используются по ссылкам на версии файлов, без обязательного копирования самих файлов.

6.2. Изменение экземпляра не изменяет заготовку и другие экземпляры. Сохранение изменений обратно в библиотеку — отдельная явная операция.

6.3. Изменение заготовки не обновляет ранее собранные материалы автоматически. Для черновика допускается явное обновление из новой редакции заготовки после предупреждения о замене локальных настроек.

6.4. Опубликованное содержание обновляется только через создание и выпуск новой версии.

6.5. У заготовок есть название, тип, язык, метки и доступ: личная библиотека или общая библиотека платформы. Авторство сохраняется при копировании доступных для этого материалов.

## 7. Контракт программного блока

7.1. Каждый тип объявляет стабильный идентификатор и версию формата данных, схему настроек, значения по умолчанию и правила валидации.

7.2. Контракт описывает редактирование, представления учителя/проектора/ученика, состояние выполнения, допустимые действия и возвращаемые результаты. Общие визуальные части могут переиспользоваться; три независимые реализации для простого блока не обязательны.

7.3. Сервер проверяет роль отправителя, параметры, допустимость действия в текущем состоянии и область действия. Проверка правильного ответа не полагается на данные, присланные браузером ученика.

7.4. Контракт определяет переводимые поля, требования к медиа, возможности работы без индивидуальных устройств и восстановление после подключения.

7.5. Тип описывает, как читать старые поддерживаемые форматы или преобразовывать их в новую редакцию. Обновление кода не выполняет скрытую перезапись опубликованных версий. Неподдерживаемый формат выявляется до запуска и даёт понятное сообщение.

7.6. Программные расширения добавляются разработчиком в доверенный код проекта и проходят обычные проверки. Учитель не загружает исполняемый JavaScript/PHP через редактор.

7.7. Программно подготовленные материалы используют те же версии, права, медиа, проведение и историю, что и материалы конструктора.

7.8. Новый тип в рамках поддерживаемого контракта регистрируется без изменения общего алгоритма движка. Если новая механика требует новой общей возможности платформы, расширение контракта оформляется как отдельное совместимое изменение.

## 8. Базовые блоки первой платформенной версии

8.1. Минимальный технический прототип содержит этап, текст, изображение и вопрос с одним вариантом ответа. «Текст с изображением» — макет сочетания компонентов, а не обязательный отдельный тип.

8.2. Полная базовая библиотека включает следующие возможности; объединение близких вариантов в один программный тип допускается.

| Возможность | Настройки и ожидаемое поведение |
| --- | --- |
| Заголовок и текст | Переводимый текст, ограниченное безопасное форматирование |
| Изображение | Выбор версии медиа, подпись, альтернативный текст, способ размещения |
| Цитата или отрывок | Текст и источник; может использовать общий текстовый компонент |
| Вопрос для обсуждения | Общий вопрос и непубличные подсказки ведущему |
| Инструкция | Задание классу, паре или группе без обязательного цифрового ответа |
| Один вариант ответа | Варианты, необязательное правильное решение, правило повторного выбора |
| Несколько вариантов | Допустимое число выборов, правило проверки, раскрытие результата ведущим |
| Опрос | Выбор без оценки правильности, агрегированные результаты |
| Свободный ответ | Ограничение длины, отправка, модерация и публикация |
| Последовательность | Элементы, порядок и момент проверки; доступная альтернатива перетаскиванию |
| Сопоставление | Пары элементов, правило проверки и показ результата |
| Роли | Список ролей, вместимость, выбор/назначение и освобождение роли |
| Готовность и вопрос | Сигнал готовности или запрос помощи; реакция ведущего/помощника |
| Итог и рефлексия | Итоговый текст, вопрос или личный ответ на основе общих компонентов |

8.3. Условия повторного ответа и раскрытия решения задаются явно. Свободный ответ не считается автоматически «правильным» или «неправильным».

8.4. Для задания с проверкой предусмотрены состояния: подготовлено, открыто, ответы закрыты, результат раскрыт. Не все типы обязаны использовать все состояния; переходы определяются контрактом.

8.5. Переход назад по этапам сохраняет ответы. Сброс упражнения, если поддерживается, является отдельным действием с понятным последствием и новым номером попытки; он не происходит при простом показе этапа.

8.6. В первой версии не требуется единая система баллов, наград и соревнований. Визуальная «волна добра» не подразумевает автоматически начисление баллов.

## 9. Медиатека

9.1. Начальный обязательный формат медиа — изображения. Конкретные допустимые форматы, предельные размеры и объём хранилища фиксируются перед реализацией загрузки; расширение на аудио/видео не входит в обязательный минимум.

9.2. Пользователь может загрузить изображение, увидеть миниатюру, задать название и метки, найти файл и вставить его в несколько материалов.

9.3. Хранятся владелец, источник/авторство, сведения о допустимом использовании, версии и места использования. В общую библиотеку попадают только материалы с установленным основанием для такого использования.

9.4. Замена файла создаёт новую Media Version. Публичные версии и начатые занятия продолжают ссылаться на прежний файл.

9.5. Подпись, альтернативный текст и кадрирование могут отличаться в разных экземплярах, использующих один оригинал. Исходное изображение при кадрировании не изменяется.

9.6. Удаление используемой версии блокируется либо заменяется архивированием. Интерфейс объясняет, где материал используется. Неиспользуемые версии удаляются по явному действию или документированной политике очистки.

9.7. Личные файлы проверяются по правам доступа. Ученик и проектор получают лишь материалы, необходимые разрешённому им представлению занятия.

## 10. Конструктор

10.1. Рабочая область содержит список этапов, область сборки и настройки выбранного элемента; из неё доступны библиотека блоков и медиатека.

10.2. Обязательные операции: создать, переименовать, скопировать и удалить этап; добавить, настроить, скопировать, переставить и удалить блок; сохранить блок в библиотеку.

10.3. В минимальном прототипе порядок меняется кнопками. Перетаскивание добавляется как удобство и не является единственным способом управления.

10.4. Доступны ограниченные готовые макеты расположения: один столбец, текст рядом с изображением, материал над заданием. Произвольное рисование элементов по пикселям не входит в первую версию.

10.5. Полный конструктор имеет автосохранение со статусом, отмену/повтор основных локальных изменений, предварительный просмотр трёх представлений и репетицию.

10.6. Неудачное сохранение показывается явно; интерфейс не сообщает об успешном сохранении неподтверждённых изменений. Несовпадение редакций при работе в нескольких вкладках не приводит к молчаливой перезаписи.

10.7. Перед выпуском версии проверяются обязательные поля, доступность медиа, настройки заданий и выбранные переводы. Ошибки ведут к соответствующему элементу редактора.

10.8. Публикация в общем каталоге требует отдельного действия и проверки администратором. Личное проведение не зависит от включения в общий каталог.

## 11. Проведение занятия и синхронизация

11.1. Session хранит фиксированную версию содержания, язык, владельца, ведущего, этап, состояния блоков, участников, ответы и таймер на сервере.

11.2. Предусмотрены состояния занятия: подготовлено, проводится, приостановлено, завершено. Истечение срока хранения/доступа обрабатывается отдельно от педагогического завершения.

11.3. Пауза занятия приостанавливает таймер и приём новых ответов и показывает участникам сообщение о паузе. При возобновлении состояния восстанавливаются; уже принятые ответы остаются. Пауза только таймера — отдельное действие.

11.4. Завершение прекращает приём ответов и сохраняет итог. Закрытие браузера, пульта или проектора само по себе занятие не завершает.

11.5. При обновлении страницы или возвращении связи клиент получает актуальное разрешённое ему состояние. Повторная отправка одной команды/ответа не создаёт дубликат.

11.6. Команды привязаны к идентификаторам занятия, экземпляра и попытки, а не к подписи или позиции на экране. Сервер отклоняет команды с устаревшими правами или недопустимым состоянием и возвращает актуальные данные.

11.7. Одновременные заявки на одну роль и передача ведения выполняются атомарно. Не допускается ситуация, когда два участника получают единственное место или одновременно становятся активными ведущими.

11.8. Таймер определяется серверным временем, временем окончания и остатком на паузе. Каждая вкладка не ведёт независимый источник истины.

11.9. Статус «подключён» определяется активностью и не удаляет участника или его ответы при краткой потере связи. Сроки определения отключения задаются конфигурацией.

11.10. Без связи интерфейс показывает состояние подключения и не выдаёт неподтверждённое действие за выполненное. Полноценное проведение офлайн не обещается.

## 12. Общие действия и действия блока

12.1. Общая оболочка предоставляет навигацию, участников, QR, таймер, сообщение классу, паузу занятия и «волну добра».

12.2. Текущий блок добавляет контекстные команды, например открытие ответов, проверку, раскрытие решения или распределение ролей. При нескольких блоках в этапе явно указан целевой блок.

12.3. Показ результатов доступен через общий интерфейс пульта, но относится к конкретному упражнению. Он не должен случайно раскрывать ответы других блоков.

12.4. «Волна добра» — кратковременный синхронизированный визуальный эффект. Событие имеет идентификатор и срок актуальности: повторная доставка не запускает его дважды, восстановление связи не воспроизводит истёкшие эффекты.

12.5. Сохраняемое состояние, например таймер или открытые результаты, восстанавливается после подключения. Кратковременные эффекты обрабатываются по правилам актуальности.

12.6. Сильные анимации должны иметь спокойный вариант для пользователей с предпочтением уменьшенного движения. События не скрывают основные кнопки управления надолго.

## 13. Пульт и представления экранов

13.1. Постоянная оболочка пульта содержит структуру занятия, текущий этап, навигацию, таймер, участников, код/QR, ответы и модерацию, заметки ведущему, быстрые действия и управление соведущим.

13.2. Предпросмотр общего экрана показывает то, что предназначено для проектора. Учительские заметки, неопубликованные ответы и служебные сведения остаются в учительской области.

13.3. Проектор получает отдельное представление только для показа. Ограничение касается серверных данных, а не только скрытия элементов через CSS.

13.4. Экран ученика адаптирован к телефону: понятное текущее задание, крупные элементы выбора, подтверждение отправки, состояние соединения и доступ к собственным разрешённым результатам.

13.5. Главное левое меню кабинета полностью скрывается за левый край, освобождая ширину. Кнопка открытия остаётся в верхней панели. Список этапов является отдельным элементом пульта.

13.6. Пульт поддерживает три представления: встроенное управление, отдельная вкладка, отдельное компактное окно браузера с обычным перемещением и изменением размера средствами ОС.

13.7. Компактный пульт сохраняет необходимые инструменты, включая ответы и модерацию; полное меню кабинета и большой предпросмотр не должны занимать его основную площадь.

13.8. После успешного открытия и подключения отдельного пульта встроенная панель скрывается, а рабочая область расширяется. Доступно действие «Вернуть пульт». Если окно не открылось, встроенное управление остаётся доступным; предлагается вкладка.

13.9. Отделение пульта не создаёт новое занятие, нового ведущего или таймер. Возврат, обновление и закрытие окна не сбрасывают данные и не завершают занятие. Закрытие основной страницы не должно лишать уже открытый авторизованный пульт возможности работать с сервером.

13.10. Открытие пульта выполняется по действию пользователя. Отдельная вкладка служит альтернативой там, где компактное окно не поддерживается или неудобно. Закрепление окна поверх всех приложений не является обязательством веб-интерфейса.

13.11. Кнопки имеют понятные подписи и состояния, доступны с клавиатуры. Длинные ответы прокручиваются, не вытесняя основные команды. Адаптивное поведение проверяется отдельно от статичного макета.

## 14. Гостевой запуск и присоединение

14.1. Опубликованный доступный материал можно начать без регистрации учителя. Для каждой новой попытки проведения создаётся отдельное занятие.

14.2. Сервер выдаёт гостю защищённый доступ владельца. Публичный код комнаты и ученическая ссылка не дают учительских полномочий; секреты управления не помещаются в обычные публичные ссылки.

14.3. Ученику нужны код/QR и отображаемое имя или псевдоним. Email, пароль и постоянный профиль ученика не требуются.

14.4. Повторное подключение с действительным доступом участника восстанавливает его данные. Одного совпадения имени недостаточно для получения чужих ответов или прав.

14.5. При регистрации или входе владелец может сохранить ещё доступное гостевое занятие в аккаунт. Перенос подтверждается его действительным гостевым доступом и не выполняется по одному коду комнаты.

14.6. Срок гостевого доступа и хранения показывается до запуска и в пульте. После истечения возвращается понятное сообщение; пользователь не должен рассчитывать на бессрочное хранение без аккаунта.

14.7. После удаления данных браузера восстановление гостевого доступа не гарантируется. Альтернативный механизм восстановления, если потребуется, согласуется отдельно; регистрация даёт устойчивую привязку к аккаунту.

## 15. Мультиязычность

15.1. Переводится интерфейс, метаданные каталога, содержание блоков, варианты ответов, инструкции, подписи и заметки ведущему.

15.2. Технические идентификаторы блоков, этапов и ответов независимы от языка. Текст ответа не используется как ключ сохранения результата.

15.3. У каждой редакции перевода есть состояния «черновик», «частично», «готов». Готовность определяется проверкой обязательных полей; отметка не заменяет редакторскую проверку качества текста.

15.4. Каталог показывает фактически доступные языки конкретной версии. Явный выбор другого доступного языка допустим; скрытая подмена отсутствующего перевода не допускается.

15.5. В первой версии язык проведения выбирается до запуска и фиксируется в занятии. Язык интерфейса учителя может отличаться. Индивидуальный перевод содержания каждому ученику не входит в обязательный минимум.

15.6. Иллюстрации по умолчанию не содержат встроенных надписей. Текст размещается средствами интерфейса. Если надпись необходима внутри изображения, создаются отдельные языковые версии с явной привязкой.

15.7. Начальные языки предлагаются RU/DE; окончательный набор фиксируется владельцем. Дополнительный язык не должен требовать переработки движка.

## 16. Кабинет учителя

16.1. Предусмотрены регистрация, вход, выход, восстановление доступа и необходимые почтовые уведомления. Конфигурация отправки писем должна быть реально проверена, а не заменена имитацией интеграции.

16.2. Разделы кабинета: обзор, мои материалы, конструктор, библиотека блоков, медиатека, история и настройки. Пульт доступен для выбранного занятия.

16.3. Учитель видит личные черновики и версии, доступные общие материалы, избранное, начатые и завершённые занятия.

16.4. История хранит дату, материал и версию, язык, статус, пройденные этапы, агрегированные результаты и заметки учителя. Подробные ответы доступны только в пределах разрешённого срока и прав.

16.5. «Продолжить» открывает незавершённое занятие. «Провести снова» создаёт новое с чистым состоянием, сохраняя прежнюю историю.

16.6. Доступны изменение настроек аккаунта и запрос/действие удаления собственных данных по утверждённой политике. Удаление аккаунта не должно оставлять доступные по старым приглашениям личные занятия.

## 17. Ответы и жизненный цикл данных

17.1. Письменный ответ сначала доступен учителю и уполномоченному помощнику. Для общего экрана и остальных учеников он становится доступен только после публикации.

17.2. Предусмотрены одобрение, отклонение, редактирование отображаемого текста перед публикацией и снятие с общего показа. Отправленный оригинал и текст для публикации различаются в учительском представлении.

17.3. Общий показ письменных ответов по умолчанию не раскрывает имя ученика. Личный результат доступен только соответствующему участнику и уполномоченным учителям.

17.4. Для сигналов «Есть вопрос» учитель/помощник может отправить предусмотренную реакцию. Она адресуется конкретному участнику и не попадает автоматически на проектор.

17.5. Сроки отдельно задаются для гостевых занятий, истории аккаунта, имён и подробных ответов, репетиций и технических событий. Точные значения утверждаются до запуска хранения реальных пользовательских данных.

17.6. Очистка подробных ответов может сохранять разрешённые обезличенные итоги и факт проведения занятия. Политика должна ясно объяснять, какие данные исчезают.

17.7. Автоматическая очистка выполняется фоновым заданием по документированным срокам; ошибки очистки доступны администратору. Резервные копии учитываются в сроках хранения и процедуре восстановления.

## 18. Совместное проведение

18.1. Владелец создаёт ограниченное приглашение помощника. Приглашение имеет срок действия и возможность отзыва; после принятия помощник получает собственный доступ, а не копию секрета владельца.

18.2. Приглашение не требует создания ученического аккаунта. Для помощника предлагается доступ к конкретному занятию без обязательной регистрации; привязка к аккаунту не должна расширять права автоматически.

18.3. Передача ведения явно выбирает получателя. Сервер меняет активного ведущего атомарно; прежний ведущий становится помощником, если не является владельцем с дополнительными полномочиями.

18.4. Команды из старых вкладок прежнего ведущего больше не исполняются как ведущие. При отключении нового ведущего владелец может вернуть управление.

18.5. Отзыв приглашения до принятия и отзыв уже выданного доступа — отдельные действия. После отзыва действующие соединения не сохраняют права при следующем обращении к серверу.

18.6. Совместное проведение не включает одновременное редактирование содержания. Помощник не может изменить опубликованную версию, удалить занятие или назначить себя владельцем.

## 19. Главная страница и каталог

19.1. Главная следует утверждённому визуальному направлению: представление проекта, подбор материалов, аудитории и темы, доступные форматы, объяснение работы и переход к материалам.

19.2. Каталог имеет поиск по названию и ключевым словам, фильтры по возрасту, теме, аудитории, формату, языку и длительности. Фильтры комбинируются, сбрасываются и отражаются в адресе для повторного открытия подборки.

19.3. Возрастные группы исходного макета: 5–7, 8–10, 11–14, 15+, взрослые. Они являются редактируемыми метаданными каталога, а не условиями внутри кода заданий.

19.4. Карточка показывает название, иллюстрацию, описание, возраст, длительность, языки и требования к устройствам/материалам. Просмотр раскрывает структуру и цели и позволяет начать без регистрации.

19.5. Предлагаемый первый вариант — просмотр выбранного материала поверх/внутри главной с прямой ссылкой на выбор. Требование иметь ровно одну публичную страницу не установлено; окончательный способ просмотра указан среди открытых решений.

19.6. В каталоге нет фиктивных уроков, скачиваний и неработающих форматов. Если материалов пока нет, показывается честное пустое состояние. Готовность механизма каталога не требует создания конкретного учебного урока.

19.7. Приватные черновики и репетиции не индексируются и не попадают в результаты публичного поиска. Ссылка сама по себе не отменяет проверки доступа.

## 20. Административные функции

20.1. Администратор управляет темами, аудиториями, возрастными группами, форматами, общей библиотекой и видимостью материалов в каталоге.

20.2. Материал, предложенный для общего каталога, проходит проверку содержания, работоспособности, переводов и допустимости использования медиа. Решение и причина возврата доступны автору.

20.3. Одобрение публичной версии не распространяется автоматически на следующую редакцию автора.

20.4. Для первой версии достаточно простой очереди предложенных публикаций и управления справочниками. Сложный редакционный workflow не является обязательным.

## 21. Визуальный стиль и генерация изображений

21.1. Утверждённый стиль главной и пульта обязателен для дальнейшей разработки и новых изображений. Нужные иллюстрации для уроков, блоков, фонов и частей интерфейса генерируются или подбираются с сохранением этого направления.

21.2. Подробные правила и готовые тексты заданий сохранены в [руководстве по визуальному стилю и генерации](IMAGE_GENERATION_GUIDE.md). Его промпты используются вместе с доступными референсами, а не как замена их визуальной проверке.

21.3. Основные признаки: тёплая светлая бумага, акварельная иллюстрация с мягкой детализацией, коричневые заголовки, янтарные акценты, приглушённая оливковая зелень и спокойные природные оттенки.

21.4. Фактура и декор не ухудшают чтение и управление. Изображения контента не превращают все экраны в перегруженные иллюстрированные плакаты; у интерфейса остаются ясная иерархия, поля и контраст.

21.5. Для каждой генерации указываются назначение, сюжет, композиция, пропорции, необходимость свободного места и прозрачности. Пользовательский текст по умолчанию остаётся отдельным переводимым слоем интерфейса.

21.6. Каждый результат проверяется визуально, сохраняется отдельной версией и добавляется в медиатеку с названием, метками и происхождением. Существующие утверждённые изображения не перезаписываются автоматически.

## 22. Техническая основа и эксплуатация

22.1. Основа этапа 1: Laravel 13, Vue 3 и TypeScript, Vite 8, Node.js 22. Минимум PHP приложения — 8.4; по уточнению владельца production использует Plesk PHP 8.5.11 FPM. Выбрана MariaDB 10.6.23; хранение предметных данных будет реализовано следующим этапом. Проверенные пути и команды окружения сохраняются в `DEPLOYMENT.md`.

22.2. Одно приложение делится на модули содержания и версий, блоков, медиа, проведения, аккаунтов, каталога и администрирования. Общие правила не дублируются в индивидуальных уроках.

22.3. База хранит структурированные данные; файловое хранилище — версии медиа. Закрытые файлы выдаются с проверкой доступа. Резервирование охватывает и базу, и используемые файлы.

22.4. Для начала предлагаются периодические запросы состояния с версиями данных и защитой от повторных команд. Нагрузочная проверка определяет приемлемую частоту. Переход на другой транспорт не меняет модель уроков и контракт блоков.

22.5. Долгие операции и очистка выполняются фоново. Необходимость отдельного обработчика очереди определяется конкретными операциями; он не добавляется только ради архитектурного названия.

22.6. Production работает в Plesk с PHP 8.4 и Node.js 22 для команд сборки. При подготовке серверных команд используются подтверждённые Plesk-пути, а не случайные версии из системного PATH.

22.7. Перед deployment устанавливаются фактический каталог проекта, ветка/upstream, Document Root, конфигурация базы, почты, хранилища, HTTPS и фоновых задач. Путь на сервере не выводится из имени домена предположением.

22.8. Настраиваются резервное копирование, проверка восстановления, health check и журнал технических ошибок без паролей, токенов и подробных ученических ответов. Для миграций определяется порядок резервирования и восстановления.

22.9. Учительский и ученический доступ разделены; предусмотрены валидация ввода, защита от подделки запросов, безопасный вывод текста, проверка загрузок и ограничения частоты запросов. Лимиты учитывают общий школьный IP и не должны необоснованно блокировать весь класс.

22.10. Сервер не отправляет ученику скрытые решения, непубличные ответы других участников и учительские заметки. Ошибки доступа проверяются напрямую на API, а не только через интерфейс.

22.11. Секреты, конфигурация окружения, реальные пользовательские данные и production-логи не добавляются в Git. Почтовые и другие интеграции не объявляются готовыми без фактической проверки.

## 24. Поэтапный план реализации

### 24.1. Этап 1 — Подготовка проекта и архитектурная спецификация

Действия: проверить доступ к указанному GitHub; безопасно подключить рабочую копию, сохранив существующие файлы; определить текущую ветку и upstream; выбрать версии стека; описать схему данных, контракт блока, права и правила версий; подготовить локальный запуск и CI.

Результат: документированные решения и воспроизводимый минимальный проект. Новая ветка или отдельная история Git не создаются без необходимости и согласования с правилами проекта.

Готово, когда проект запускается по README, базовые проверки воспроизводимы, содержание отделено от состояния занятия и уточнены решения, необходимые следующему этапу. Готовых учебных уроков не требуется.

### 24.2. Этап 2 — Минимальный конструктор вместе с движком

Действия: реализовать этап, текст, изображение и вопрос с одним ответом; простой редактор порядка и настроек; сохранение; минимальную серверную сессию; пульт, проектор и присоединение участника.

Результат: полная цепочка «создал → настроил → сохранил → запустил → показал → получил ответ». Используется реальный серверный путь, а не только визуальная имитация.

Готово, когда техническая сборка работает на учительском и ученическом экранах, после обновления страницы сохраняет состояние и не раскрывает закрытые учительские данные. Это промежуточный прототип, не вся первая версия.

### 24.3. Этап 3 — Проведение и удобный пульт

Действия: завершить QR/код, участников, навигацию, таймер, паузу, восстановление, общие действия и «волну добра»; реализовать утверждённое оформление, скрываемое меню и отделяемый пульт.

Результат: устойчивое управление одним занятием с разных учительских представлений, включая компактное окно.

Готово, когда проверены повторные команды, потеря связи, закрытие/возврат пульта, скрытие меню и независимость двух занятий. На этом этапе ещё не требуется приглашение другого учителя.

### 24.4. Этап 4 — Библиотека блоков и медиатека

Действия: реализовать заготовки и независимые экземпляры, поиск и метки, загрузку и выбор изображений, версии файлов, места использования и безопасное архивирование; подготовить необходимые базовые изображения по руководству стиля.

Результат: блоки и медиа действительно используются повторно, без копирования программы урока и без автоматического изменения опубликованного содержания.

Готово, когда одна заготовка и одно изображение применены в нескольких технических сборках, локальная правка не затронула остальные, а новая версия изображения не изменила старый запуск.

### 24.5. Этап 5 — Базовые интерактивные возможности

Действия: последовательно добавить остальные возможности раздела 8, модерацию и контекстные действия. Для каждого типа определить проверки и восстановление состояния.

Результат: библиотека упражнений, независимая от конкретной темы.

Готово, когда каждый тип проходит заявленные состояния, несколько блоков работают в одном этапе, повторное использование не смешивает ответы и упражнение можно проверить без разработки отдельного урока.

### 24.6. Этап 6 — Кабинет и полноценный конструктор

Действия: регистрация и почта, личные материалы, версии, автосохранение, отмена основных правок, предпросмотр/репетиция, избранное, история, продолжение и перенос своего гостевого занятия в аккаунт. Минимальная идентичность и проверки собственности используются уже на ранних этапах; здесь завершается пользовательский workflow.

Результат: учитель самостоятельно готовит и повторно использует материалы и возвращается к своим занятиям.

Готово, когда весь путь проходит через UI, ошибки сохранения видимы, черновики не становятся публичными, а история отделяет продолжение от нового запуска. Политика хранения реализована с утверждёнными сроками.

### 24.7. Этап 7 — Совместное проведение

Действия: приглашения, отдельный доступ помощника, передача ведения, отзыв, восстановление управления владельцем и соответствующие элементы пульта.

Результат: несколько уполномоченных учителей помогают в одном занятии при одном активном ведущем.

Готово, когда проверены принятие и истечение приглашения, отзыв действующего доступа, устаревшие команды и потеря связи ведущим, включая отдельные окна пульта.

### 24.8. Этап 8 — Публичная часть и публикации

Действия: главная по макету, каталог, поиск и фильтры, просмотр, публичный гостевой запуск, административная проверка материалов и справочники.

Результат: посетитель может найти действительно опубликованный материал и начать занятие без регистрации. Механика проверяется тестовыми данными; наполнить публичный каталог реальными уроками можно отдельной задачей.

Готово, когда фильтры соответствуют реальным данным, прямые ссылки работают, права на личные материалы сохраняются, готовность переводов проверяется, а пустой каталог отображается честно.

### 24.9. Этап 9 — Приёмка платформы и подготовка production

Действия: пройти итоговую матрицу проверок, проверить согласованную нагрузку и браузеры, доступность, переводы интерфейса, совместимость версий; настроить подтверждённое окружение Plesk, резервирование, фоновые задачи и health check; подготовить deployment-инструкцию.

Результат: первая платформенная версия готова к разрешённому владельцем развёртыванию. Этот этап дополняет проверки предыдущих этапов и не заменяет их.

Готово, когда критерии раздела 26 подтверждены, ограничения задокументированы, команда развёртывания использует реальный серверный путь и проверены восстановление/откат в пределах согласованного процесса. Фактический production deployment выполняется только по прямой команде владельца.

### 24.10. Последующее наполнение

После готовности платформы добавляются конкретные уроки, переводы контента, новые заготовки, изображения и дополнительные программные механики. Ни один заранее выбранный урок не является обязательным экзаменом для завершения платформенных этапов.

## 26. Итоговые критерии готовности

26.1. Учитель без программирования создаёт материал из нескольких типов блоков, сохраняет и выпускает личную версию.

26.2. Он повторно использует заготовки и изображения в других материалах, не связывая их состояния выполнения и не меняя старое опубликованное содержание.

26.3. Занятие запускается, участники подключаются по QR/коду, проектор и ученики получают разрешённые представления, ответы принимаются и модерируются.

26.4. Навигация, таймер, общие действия и контекстные команды работают через один движок. Закрытие или отделение пульта не завершает занятие.

26.5. Скрываемое меню, отдельная вкладка и компактное окно освобождают место и пригодны для небольших экранов.

26.6. После обновления или обрыва связи восстанавливается актуальное состояние без дубликатов и повторного воспроизведения истёкших эффектов.

26.7. Аккаунт сохраняет материалы и историю; незавершённое занятие можно продолжить, завершённое — повторить отдельным запуском.

26.8. Помощник подключается с ограниченными правами; передача и отзыв ведения работают на сервере и во всех открытых представлениях.

26.9. Интерфейс и содержание поддерживают выбранные языки, а незавершённые переводы не маскируются под готовые.

26.10. Публичный каталог и гостевой запуск работают, частные материалы защищены. Наличие заранее заданного конкретного урока не требуется; пустые состояния корректны.

26.11. Разработчик добавляет тип блока через стандартный контракт, а старые поддерживаемые версии продолжают выполняться.

26.12. Новые изображения соответствуют утверждённому стилю, визуально проверены, сохранены как версии и доступны для повторного использования.

26.13. Проверки качества, доступа, восстановления и согласованной нагрузки пройдены; README и эксплуатационная инструкция соответствуют реально проверенным командам. Неподтверждённые проверки не отмечены выполненными.
