# Архитектура платформы

Документ описывает ядро этапа 1 и минимальные persistence/runtime этапа 2. Будущая библиотека, медиа и совместные роли отделены от уже реализованной вертикали.

## Что реализовано на этапе 1

Приложение использует Laravel 13, PHP 8.4+, Vue 3, TypeScript и Vite 8. HTTP-слой включает страницы/API кабинета, конструктора, пульта, проектора и ученика. Файловые cache/session и синхронная очередь сохранены; запросы одной cookie-сессии сериализуются через file lock. Независимое доменное ядро по-прежнему не читает и не записывает БД.

`app/Domain/Lessons` — PHP-доменная модель, отделённая от Laravel и транспорта. Неизменяемые DTO документа, этапа и экземпляра блока создаются после строгой проверки входного JSON-совместимого массива. Домен не рендерит HTML и не исполняет пользовательский код.

`BlockRegistry::core()` регистрирует три типа версии 1: `core.text`, `core.image`, `core.single-choice`. Пара `(type id, schemaVersion)` должна быть зарегистрирована явно; дубли и неизвестные пары отклоняются. Расширения добавляются доверенным PHP-кодом через `BlockType`, а не именем класса или инструкцией из документа. Каждый тип проверяет собственные поля содержания, конфигурации, медиа и решения. Неизвестные поля и неверные типы значений отклоняются; автоматических преобразований старых схем нет.

`LessonDocument::fromArray()` проверяет версии схемы, локали и полноту переводов, форму данных, идентификаторы и уникальность этапов и блоков. Порядок задаётся списками. Для блока с выбором варианты связываются стабильными `optionId`; порядок и тексты переводов могут различаться. Языки UI RU/DE не ограничивают локали документов.

Проекции `Teacher`, `Projector` и `Student` содержат одну явно запрошенную локаль. Только teacher-проекция включает решения блоков и заметки этапов; projector/student получают публичное содержание активного этапа. HTTP/application слой проверяет владение или участие до выбора аудитории. Полный `toArray()` содержит закрытые данные и передаётся только владельцу в редакторе.

`ReleasedLesson` и `BlockTemplate` — неизменяемые доменные снимки. Выпущенная версия документа отделена от черновика, а вставка заготовки создаёт новый ID экземпляра и сохраняет происхождение версии заготовки. В домене нет хранения этих снимков, прав доступа, редактора, каталога заготовок или механизма публикации. Выпуск версии урока сам по себе не означает её публичность в каталоге.

Подробная форма полей и примеры зафиксированы в [контракте блоков](BLOCK_CONTRACT.md).

## Целевая схема постоянного хранения

Реализованы models и additive migrations `LessonMaterial`, `LessonVersion`, `TeachingSession`, `SessionParticipant`, `SessionAnswer`. Production использует MariaDB 10.6.23, локальные проверки — SQLite. Ниже исходная целевая схема: её сущности реализуются последовательно, имена минимальной реализации приведены выше.

| Сущность | Назначение и границы |
| --- | --- |
| `Lesson` | Идентичность материала как целого: стабильный ID, владелец/доступ и ссылка на текущую редакцию по мере появления соответствующей модели доступа. Не содержит изменяемый документ напрямую. |
| `LessonVersion` | Неизменяемая редакция урока и её состояние выпуска. Документ хранится как JSON и включает упорядоченные `stages` и `BlockInstance` с локализованным content, config, ссылками на медиа и закрытым solution. Новые правки создают новую редакцию, не переписывая выпущенный снимок. |
| `BlockTemplate` | Идентичность переиспользуемой заготовки блока; сами выпущенные редакции заготовки должны иметь стабильные version ID и проверенный снимок. Вставленный экземпляр копирует данные версии и хранит `origin` (template ID/version ID), поэтому дальнейшая правка заготовки не меняет урок. |
| `MediaAsset` | Идентичность медиа-объекта и его права/метаданные. Файл лежит во внешнем файловом хранилище, а не в JSON урока. |
| `MediaVersion` | Неизменяемая версия файла с ключом хранения, MIME-типом, размером, контрольной суммой и метаданными обработки. Блок ссылается на стабильные `assetId` и `versionId`, как требует контракт. |
| `LessonSession` | Отдельное конкретное проведение на основе зафиксированной `LessonVersion`, со своим состоянием, порядком/текущим этапом и временем жизни. Состояние занятия не записывается обратно в документ урока. |
| `LessonSessionParticipant` | Связь участника с проведением и его роль/состояние участия. Ответы и прочие runtime-данные относятся к проведению и участникам, а не к редакции материала. |

Структурный JSON документа остаётся проверяемым контрактом приложения. БД обеспечивает идентичность, ссылки и транзакционные границы сущностей; предметные данные каждого блока валидирует зарегистрированная версия `BlockType`. `StudioService` сохраняет полный JSON, фиксирует released-редакцию и создаёт новый draft при следующей правке. Явный `current_version_id` исключает неоднозначность временных меток. `RuntimeService` ссылается на конкретную released-версию, хранит навигацию/участников/ответы отдельно. Optimistic revision проверяется под row lock. SQL-сравнение block ID использует binary collation, как строгое сравнение домена.

`GuestIdentity` создаёт owner UUID только в серверной cookie-сессии. Имя ученика не даёт прав: credential участия — серверная связь session ID/participant ID. Код комнаты разрешает только присоединение ученика; projector token разрешает только чтение публичного экрана. URL кабинета/пульта сам по себе не авторизует владельца. Polling раз в две секунды очищается при уходе страницы и игнорирует устаревшие ответы после команды. Запись ответа и навигация сериализуются блокировкой одного занятия. Переход назад не удаляет ответы.

HTTP контракт и ограничения: [STAGE2_API.md](STAGE2_API.md). Сохранение документа исключено из Laravel trim/null transforms, чтобы пустые optional notes/caption и намеренные пробелы сохранялись; обязательные поля по-прежнему проверяет домен.

Публичность каталога — отдельное состояние доступа/публикации. Статус `released` означает зафиксированную личную редакцию и не должен трактоваться как `catalog public`.

## Будущие роли и протокол проведения

Во время проведения роли и команды будут проверяться сервером в контексте конкретного `LessonSession`. Учитель-владелец управляет занятием; приглашённый соведущий получает только явно делегированные возможности. Участник может отправлять только разрешённые действия своего участия. Проектор получает публичное представление состояния. Сервер выбирает teacher-проекцию только после авторизации. Раскрытие решения ученикам и проектору будет отдельным разрешённым runtime-действием; запрос teacher-аудитории клиентом сам по себе не даёт доступа к решению.

На этапе 2 реализованы владелец-гость, ученик и read-only проектор, переходы этапов, код присоединения, ответы и восстановление текущего состояния после обновления страницы. Таймер, завершение, раскрытие решения ученикам, полноценное переподключение и соведущие остаются следующими этапами; `Audience` не заменяет authorization.

## Текущие ограничения

- Нет регистрации/входа, восстановления доступа гостя и совместного проведения. Владение ограничено текущей cookie-сессией.
- Есть ручное сохранение полного валидного документа; autosave и неполные переводы ещё не поддерживаются. Новый язык содержания через UI пока не добавляется.
- Встроенный manifest проверяет точную пару asset/version и существование PNG; загрузка файлов, права медиа и полноценная медиатека отсутствуют.
- `BlockTemplate` остаётся доменным DTO, без persistent библиотеки заготовок. Конструктор создаёт новые экземпляры трёх общих типов; готовые темы не требуются.
- Таймер, пауза, reset/attempt, «волна добра», компактный отделяемый пульт и история завершённых занятий не реализованы.
- Нет публичного каталога, поиска, фильтрации и процесса публикации. Выпуск снимка не открывает его публике.
- Начальные словари RU/DE относятся к интерфейсу. Список поддерживаемых языков содержания и редактор незавершённых переводов остаются отдельными решениями.

## Следующее архитектурное направление

Следующий ограниченный блок — этап 3: проведение и удобный пульт, включая таймер/паузу, повторные команды, восстановление, «волну добра» и отделяемое управление. Библиотека/медиа, аккаунты, совместные роли и каталог добавляются своими этапами ТЗ.
